# Decision Log

## Cross-board join is sector-level only

Deal Name (155 distinct values in Deals, not unique — e.g. "Sasuke" appears twice, "Sakura" three times) vs. Work Orders' "Deal name masked" (58 distinct) overlap on only 52 names — not a reliable foreign key. Client Code (`COMPANYNNN` in Deals) vs. Customer Name Code (`WOCOMPANY_0xx` in Work Orders) have zero overlap — different coding schemes entirely.

Sector/service (Deals) and Sector (Work Orders) are both clean, high-fill fields, so `analyze_cross_board` joins exclusively on sector and always returns a mandatory `join_caveat` field stating the comparison is sector-level, not deal-level. The implementation never references `client_id` or `deal_name` in its join logic (enforced by `tests/test_bi_cross_board.py`).

## Revenue basis defaults to contract value excl. GST

When a user asks for "revenue" without qualifying it, `analyze_revenue` defaults to `contract_value_excl_gst` (the more conservative, tax-independent figure) rather than billed value (incl. GST) or receivable. The orchestrator infers the basis from user phrasing first (`infer_revenue_basis` in `app/bi/revenue.py`) — "billed"/"invoice" implies incl-GST, "receivable"/"outstanding" implies receivable — and only falls through to the default when phrasing gives no signal. The chosen basis is always labeled explicitly in the response; the tool never emits a bare "revenue" number.

## Closure-probability categories are reported as-is, never numerically weighted

High/Medium/Low counts are surfaced directly in `analyze_pipeline`. No invented numeric win-probability (e.g. High=80%) is applied, since the source data has no such documented mapping and inventing one would violate the no-hallucination policy. 258 of 346 Deals rows in the dev data have no closure-probability value at all — these are tracked separately as `unclassified_confidence_count`, never folded into "Low."

## Header-echo rows are structurally invalid, not missing data

Two rows in the Deals dev data are literal repeats of the header row (e.g. a "Deal Status" column containing the text "Deal Status" as its value), with a stray Deal Name and everything else blank — a copy/paste or sheet-merge artifact. `is_structurally_valid` (`app/validate/row_validity.py`) drops the entire row before normalization when it's a full echo of the header, counting it as `structurally_invalid_dropped` — distinct from and not counted toward data-quality exclusions.

Originally this checked "any single column's text equals that column's own title." Validated against the live evaluation boards (2026-08-30), that heuristic produced a 57% false-positive drop rate on Deals (193/336 rows): the eval boards' column titles are themselves masked to one of the column's own sample values (e.g. a status column literally titled "Renewables", a numeric-owner-code column titled "OWNER_001"), so any ordinary row that happened to hold that exact value in that one column was wrongly flagged as corrupted. The rule now requires *every* filled non-name column in the row to match its own title (matching the original dev-data description — "everything else blank" — rather than one coincidental match); confirmed to drop exactly the same 2 rows in the dev-data fixture and 0 rows on the live boards. Residual limitation: a handful of genuinely-corrupted echo rows from *before* the eval board's titles were masked (their value is the old, unmasked title text, e.g. a sector value of literally "Sector/service") can no longer be caught this way, since they no longer match the *current* masked title. Low-volume (~2 rows/board) and the system's own "preserve unknown values, don't force a category" rule (system-prompt §5) already handles the fallout reasonably — it surfaces as an odd extra category rather than corrupting a real one.

## Canonical field mapping needs a value-shape fallback, not just alias + type, on a masked board

Validated against the live evaluation boards: with column titles masked to sample values (see above), alias-based mapping fails for every field whose title isn't among the hardcoded aliases, and the original type-only fallback (`monday_types`, binding only when exactly one unclaimed column of that type remains) silently failed to resolve `sector` and `stage` on Deals — both fields materially used across the BI engine (sector: cross-board join, sector/leadership/pipeline filtering; stage: pipeline breakdown) — because several same-typed columns were ambiguous. `sector` in particular would have silently broken `analyze_cross_board`, which joins exclusively on it.

`resolve_column_mapping` (`app/canonical/mapping_utils.py`) gained a second fallback, `value_pattern`: when no fixed `expected_values` domain applies, bind to whichever unclaimed candidate column has the highest share of sampled values matching a regex shape (only if a ≥60% majority matches), rather than requiring a single unambiguous type-match. Used for `owner_id`/`client_id` (`OWNER_\d+`/`COMPANY\d+` — also fixes the `ar_priority`/data-quality report showing them as 0% filled when the data was actually present) and `stage` (the `<letter>. <description>` pipeline-stage convention observed on the live board). `sector` got a hardcoded `SECTOR_DOMAIN` list (same category of fixed business vocabulary as `DEAL_STATUS_DOMAIN`/`CLOSE_CONFIDENCE_DOMAIN`), matched via the existing `expected_values` overlap fallback. `product_type` and the three Deals date fields (`expected_close_date`/`actual_close_date`/`created_date`) remain deliberately unmapped on this board — 3 ambiguously-typed date columns with no distinguishing signal and no field usage elsewhere in the BI engine, so a forced guess would be strictly worse than surfacing "unmapped" (the project's own stated principle, §3/mapping_utils.py docstring).

Separately, Work Orders' `billed_value` field's alias didn't match the live board's actual column title wording ("Billed Value in Rupees (Incl of GST.) (Masked)" vs. the hardcoded "Billed Value (Incl GST) (Masked)") — added as an additional exact alias. And `_normalize_ar_priority` only recognized generic boolean tokens (true/yes/checked/...), not the live board's actual single-option label "Priority" — added to the truthy set.

## Fields that are 0% filled across the whole dataset are dropped from the canonical model, not reported per-record

Collection status, Expected Billing Month, and Actual Collection Month are 0/176 filled in the Work Orders dev data. They are omitted from `CanonicalWorkOrder` entirely (a structural absence) rather than modeled and then reported as "0% filled" on every relevant answer. `build_quality_report` additionally guards against this at the report level: any modeled field that happens to be 0% filled in a given fetch is named once in `dropped_fields` rather than listed in `fields` with `fill_rate=0.0`. This could differ in the evaluation environment if that board has these fields populated — if so, they would need to be added back to the canonical model.

## Response formatting boundary: Python renders structure, Gemini writes only the Insight

Every BI tool returns exact, already-computed numbers. `app/agent/formatting.py` renders the Answer/Key-metrics/Data-quality sections directly and verbatim from that typed result — Gemini never sees a chance to restate or re-derive a number. Gemini's role, enforced via an explicit instruction appended to the system prompt (`app/agent/system_prompt.py`), is to write only the "Insight" paragraph (or, for a leadership update, the Executive Summary and Key Takeaway). This keeps all arithmetic in code (system-prompt §20/§21) while still producing founder-level narrative, and avoids a second LLM call per turn.

**This boundary was originally instruction-only, with no code-level enforcement.** Live testing against `gemini-2.5-flash` (2026-08-30) showed the model does not reliably comply: on an `analyze_cross_board` call it wrote a full duplicate `### Answer / ### Key metrics / ### Insight / ### Data quality` block inside the Insight text instead of one short paragraph, and on `generate_leadership_update` it followed §23's full seven-section structure (Pipeline, Operations, Financial, ... as its own markdown headers) rather than the narrower "Executive Summary + Key Takeaway only" the implementation note actually asks for — both duplicating content `render_metrics` already renders from typed data. `app/agent/formatting.py` now enforces this structurally: `_strip_duplicated_structure` truncates the Insight at the first `Answer`/`Key metrics`/`Insight`/`Data quality` heading for every other tool, and `_extract_leadership_insight` keeps only the text under `Executive Summary`/`Key Takeaway` headings for `generate_leadership_update`, discarding any other section the model adds. Confirmed live: both paths correctly strip the duplicated/out-of-scope content while leaving genuine Executive-Summary/Key-Takeaway prose intact. Residual, not fixed: on cross-board comparison questions specifically, the model tends to skip free-form prose entirely and jump straight to its own structured breakdown, so the Insight sometimes falls back to a generic "See the metrics above" placeholder instead of a real qualitative read of the numbers — safe (no wrong/duplicated data), but weaker than ideal; worth another system-prompt pass if it matters for the eval.

## Session and cache mechanism: KV-backed on Vercel, in-memory locally

Session state (conversation history, last-resolved slots for multi-turn inheritance) is keyed by a client-generated UUID (stored in the browser's `localStorage`, sent in the request body — no cookies). Fetched-and-normalized board data is cached (shared across all users, since both boards are the same for everyone) with a 2-minute TTL; it is never presented as more current than that.

Originally both lived in a module-level dict, which is correct only for a single long-lived process. Deploying to Vercel's serverless Python runtime means the process (and that dict) can be torn down between invocations, so both stores now go through `app/kv_store.py`, a thin async client for Vercel KV / Upstash Redis's REST API (`app/data_cache.py`, `app/agent/session.py`). When `KV_REST_API_URL`/`KV_REST_API_TOKEN` aren't set — local `uvicorn` dev — both fall back to the original in-process dict, so no KV instance is required to develop locally. Session entries expire after 1 hour (KV `EX`); the board cache still uses `board_cache_ttl_seconds` (2 minutes).

## Deploy target: Vercel (serverless)

`api/index.py` is the single entrypoint — it imports the one FastAPI instance from `app/main.py` rather than splitting routes across multiple `api/*.py` files, which Vercel would otherwise treat as separate isolated functions unable to share state. `vercel.json` uses the current `functions` + `rewrites` config (the legacy `builds`/`routes` format can't carry `maxDuration` — those two top-level keys are mutually exclusive in Vercel's schema); Vercel auto-detects the Python runtime for `api/index.py` from the root `requirements.txt` without an explicit builder.

Both boards are now fetched in parallel (`asyncio.gather` in `app/data_cache.py`) rather than sequentially, since a cold Monday fetch for both boards plus the Gemini tool-calling loop can otherwise approach the default 10s function timeout. `vercel.json` sets `maxDuration: 60` on `api/index.py`, which this project deploys to a Pro-tier project to actually honor — **on Hobby that value is clamped/rejected and becomes a no-op**, in which case the parallel fetch and a minimal Gemini tool-loop are what keep a turn inside 10s, not this setting.

An earlier version of this log recommended a persistent-process host (Render/Railway/Fly.io) instead, on the grounds that serverless would silently break both in-memory stores. That's still true of the *original* implementation; the KV-backed stores above are what make the Vercel target viable.
